# Alpha 3 commit-ordered Workspace sync

`workspace_sync_state` maintains one bigint revision per Workspace. `workspace_changes` contains only Workspace/revision/kind/object UUID/operation/time, not photo URLs, notes or geometry. Every business insert/update/delete records an invalidation in the same transaction; media changes, including photo deletion, upsert-invalidate the surviving parent Observation. A removed Workspace does not recreate a change-log row during cascading cleanup. Unchanged rows touched only by updated_at do not produce events.

Revision allocation updates the Workspace state row under a transaction-held row lock. This serializes same-Workspace mutations in commit order; rollback removes both counter increment and event. A global sequence or updated_at alone would allow a later committed cursor to skip an earlier still-open transaction. Ordinary application transactions affect one Workspace; future multi-Workspace batch writes must lock Workspace IDs in consistent order to avoid deadlock. This write serialization has a throughput cost; no claim of unlimited write scalability.

`landos_workspace_changes` is SECURITY INVOKER, authenticated only, fixed empty search path and membership check; both new tables have Workspace RLS and client SELECT only. The private SECURITY DEFINER trigger is non-exposed, PUBLIC/anon/auth execution revoked, checks active writer membership when auth.uid exists, and only records its business row's Workspace/ID. Administrative/service-role imports already bypass ordinary CRUD RLS; they are not a public trigger-call path.

Bootstrap (after omitted) returns committed head with no events. Anchor it **before** viewport snapshots. For deltas, after is exclusive; first page fixes until/head watermark, later pages reuse it. Ordering is (Workspace, revision), unique bigint with string transport to avoid JS precision loss. Insert/update are upsert invalidations; deletion is a tombstone retained in the log. Current rows are read under normal RLS; if they have since disappeared they are returned as delete. This is latest-state reconciliation, not historical point-in-time row replay. Newer commits are caught on the next fixed-watermark round.

`/api/map/changes` validates cursor/Workspace/bbox and batches at most 100 events. Exact viewport intersection decides upsert/removal; viewport-only removals do not erase the saved sidebar entity. Photo signatures use existing private scoped cache. Layer headers are lean; open complete-layer collections update by feature identity. Read a complete current layer again before mutation. All credentials remain public-client appropriate except non-callable internal trigger privilege.

The current map polls every ten seconds while visible, and on focus/visibility restore. Superseded viewport/account responses are ignored/aborted. Cursor advances only after applying changes; old viewport caches are cleared on invalidation. It applies at most ten pages per round, continues next round on backlog and retains the bounded 500-record/category viewport cap. The initial snapshot and explicit Refresh remain reconciliation paths for cap overflow; no offline map is introduced. Change-log retention/reset and large write-throughput baselines remain future work; do not prune tombstones until a safe reset/retention contract exists.

Tests include owner/nonmember/anonymous SQL permissions, client event forgery rejection, stable pages/deletion watermark, pure create/update/delete reconciliation and two real browser sessions receiving automatic create/update/delete without reload. Physical device/background behavior remains NOT TESTED until signed acceptance.

Deterministic concurrent-writer verification now runs in `db:test` through tests/sync-concurrency.py, which refuses any container outside the disposable `land-banker-rls-test-<pid>` naming pattern. A holds an uncommitted business write; B is observed waiting on a real PostgreSQL lock; an authenticated third reader sees committed head zero, not the uncommitted revision. After A then B commit, both identities appear in order; a subsequent rollback leaves no head/event residue. This validates the cursor race directly, not high-write performance. No hosted/MaxQI data is touched by this test.

Lock review against Supabase Postgres Best Practices: external government/media HTTP work is outside write transactions; ordinary layer RPCs stay within one Workspace. The deterministic writer test is not proof that every custom multi-row lock order is deadlock-free. A custom writer that first holds a business row while waiting for the Workspace counter can conflict with another writer that already holds that counter and later needs the business row. PostgreSQL aborts/rolls back a victim, so its event is not committed; callers must retain drafts and retry the whole idempotent transaction. Future bulk/multi-table RPCs should lock Workspace counters first in canonical Workspace order, then business IDs in consistent order, with bounded database transaction timeouts. Do not extend a write transaction around network calls or claim a high-write throughput guarantee.
