# Remote terrain evaluation

No remote DEM is enabled for production. The only approved data used in the proof so far is the GA SRTM-derived 1 second DEM v1.0 (CC BY 4.0, EGM96, roughly 30 m source resolution). Its five committed local proof tiles are fixtures, not a nationwide service. Attribution and limitations are in `TERRAIN_GA_POC.md`.

## Direct remote tiles

The [AWS Registry Terrain Tiles](https://registry.opendata.aws/terrain-tiles/) lists global Mapzen/Tilezen data, and the [Tilezen endpoint documentation](https://github.com/tilezen/joerd/blob/master/docs/use-service.md) identifies 256-pixel Terrarium PNGs in the public S3 bucket. A bounded `HEAD` for an Alpine tile returned HTTP 200, 63,122 bytes and `x-amz-meta-x-imagery-sources: srtm/S37E148.tif`. HEAD requests with `Origin: https://landbanker.vercel.app` omitted `Access-Control-Allow-Origin`, but a subsequent GET with that origin returned `Access-Control-Allow-Origin: *`. The GET result supports browser access; an actual browser integration test remains necessary. Tilezen's documentation describes the bucket for EC2 usage, not a guaranteed production browser tile service; A [Tilezen member stated in May 2025](https://github.com/tilezen/joerd/issues/223) that the AWS dataset has no usage limits. That statement does not document an uptime commitment or explicitly resolve commercial multi-user hosting terms; those and the budget remain unverified. Its [attribution and source documentation](https://github.com/tilezen/joerd/blob/master/docs/data-sources.md) describes a mosaic, varying source resolutions, older releases and oversampling. It must not be labelled as a uniform GA SRTM/EGM96 dataset without per-tile provenance and datum verification. The terrain controller now permits either 256- or 512-pixel Terrarium tiles, but no source is automatically configured.

[OpenTopography's developer terms](https://opentopography.org/developers) state that integration of their API into commercial software requires an Enterprise key. Public data licensing does not make the free key suitable for this use. No key was requested or embedded.

## GA WCS conversion

Three sequential conversions of the same bounded GA Alpine tile using `scripts/terrain/ga_srtm_tile.py` in this runtime completed in 3.53, 3.41 and 2.04 seconds wall time, producing 542,300-byte PNGs. The maximum child-process RSS observed across those runs was 78,828 KiB. This is a small, warm-environment measurement, not a throughput, cold-start, concurrency or uptime guarantee. There was one WCS request per conversion; cache hit rate was not measured. Extrapolating ten uncached tiles implies ten WCS calls and approximately 20–35 seconds of summed conversion work, though concurrent elapsed time and source load are unknown.

Do not deploy a public on-demand WCS conversion endpoint yet. Open-data reuse rights do not establish acceptable request rates to the WCS. Global rate limiting, request coalescing, denial-of-service protection, cache retention, invalid/no-data handling, metering, and source-operator capacity/permission would need to be established. A Python/GDAL runtime and its memory/cold-start and Vercel plan constraints also require verification. No new infrastructure was provisioned.

## Cost illustration, not a quote

The five GA proof PNGs total 2,426,966 bytes: mean **485,393 bytes** per tile. A hypothetical 1,000 map sessions with ten uncached tiles each would transfer about **4.85 decimal GB** of response bodies; actual requests per session and cache hit rates have not been measured. [Vercel CDN pricing](https://vercel.com/docs/manage-cdn-usage) charges for transfer and requests, and [regional pricing](https://vercel.com/docs/pricing/regional-pricing) lists a regional fast-transfer rate range of $0.15–$0.35/GB for the relevant overage tier. Illustratively, if all 4.85 GB were billable overage at those rates, transfer alone would be about **$0.73–$1.70**, excluding requests, function execution, source access, storage, taxes and any included usage. The active plan, region, cache hit rate and traffic are unknown, so this is not an estimate of the user's actual bill.

The smallest further alternatives are (1) obtain an explicit agreement and CORS-capable commercial-use tile endpoint with documented limits, or (2) establish GA WCS request permission and a tested, bounded caching and conversion service with a spending cap. Costs for either cannot be quoted from the available evidence. Do not enable either or deploy terrain until usage, datums, security, costs and live map/parcel checks are resolved.

## Coverage reporting

The workspace examines MapLibre's rendered terrain coverage index and warns if any rendered terrain tile lacks a DEM sampler or the state is unknown; this is stricter than checking only the map centre. It cannot identify missing values encoded *inside* a loaded raster tile or establish the source's accuracy. Sampling refuses points with no drawn DEM and preserves confirmed zero values. Unknown resolution, datum and accuracy are explicitly labelled; never compare or combine heights across unknown or incompatible datums. The index is a MapLibre 6.16 API and must be revalidated on upgrades.

A separate 1024×768 synthetic-fixture browser test requested 6 distinct DEM tiles initially and 2 additional tiles after one pan. Each synthetic fixture is 51,438 bytes, so these represent approximately 309 kB and 103 kB of fixture response bodies respectively. These counts are from one local test with one map movement; they are not a real-provider traffic model, production cache-hit measurement or reliable estimate for all sessions. The bounded real GA proof tile is much larger and the Tilezen sample is 63,122 bytes, so transfer varies by provider, geography and encoding.

Five additional bounded AWS GETs at zoom 11 all returned CORS `*`: Vermont South 30,423 bytes, Balliang 42,312, Lismore 41,120, Dunoon 50,190 and Alps 63,122. Their S3 `x-amz-meta-x-imagery-sources` headers named SRTM in all five; Vermont South, Balliang and Dunoon additionally named GMTED. This confirms a mosaic exists in individual test tiles, not the exact per-pixel provenance or a consistent datum; the dataset must not be labelled uniformly as GA 30 m EGM96 based on those headers alone. Mean sample size was 45,433 bytes. These are five requests, not a production throughput or reliability test.

Latest verification: lint, typecheck, 48 Node unit tests, two offline GA tile tests and production build passed. The synthetic terrain navigation test passed; the GA proof's centre-sampling and visible-gap-warning checks passed at all five locations on desktop and at the Alpine point on mobile. Parcel multi-select, drawing-recovery and MapLibre workflow regressions passed with the disposable local backend and fixtures. These do not establish live provider terms, continuous nationwide coverage or live VIC/NSW parcel alignment; Chromium's proxy certificate mismatch remains unresolved. No production release was made.

## Live Tilezen test, 29 October 2026

Tilezen is exposed only behind a development-build test flag; its commercial hosting terms and consistent vertical datum remain unverified. Profiles and parcel calculations are withheld for this provider until datum consistency is verified. Configured providers can use HTTPS TileJSON or XYZ Terrarium, 256/512 pixels, explicit attribution and metadata. Provider switching removes only the terrain source and hillshade layer, and clears old measurements.

A direct AWS Chromium test with TLS validation enabled sampled five centres: Vermont South 112.8 m, Balliang 195.3 m, Lismore 13.0 m, Dunoon 153.8 m, Alps 1,742.7 m. These are raw, approximate Tilezen values with unverified datum and should not be compared as official AHD heights. The basemap was a synthetic test fixture. The first desktop run recorded 114 requests (75 distinct), 106 HTTP 200 responses, eight `net::ERR_ABORTED` requests and approximately 5.14 MB of response bodies. Mean measured successful body size was 50.9 KB; no disk-cache responses were observed. One test pan requested one new distinct tile; a zoom requested two more. It reached exaggeration and hillshade controls, but timed out finishing a drawn profile, so it did not pass the full browser workflow. This single run does not predict typical usage or establish cache hit rates.

Chromium previously failed to initialise its NSS database due to workspace sandbox restrictions, not a confirmed server TLS defect. With the user's explicit approval, the existing environment proxy CAs were imported into the scoped Chromium NSS database (backed up before modification), and browser execution was given filesystem access to that database. Direct AWS, VIC and NSW HTTPS endpoints then returned HTTP 200 with normal certificate validation. This resolves the test-environment trust blocker, but does not itself verify official parcel alignment.

Follow-up live Tilezen tests: a desktop Alpine run passed the tested interaction sequence with 41 HTTP responses, zero request failures and an approximately 58.8 KB mean response body; its drawn profile correctly reported that calculations are unavailable because datum consistency is unverified. A mobile Alpine run passed with 11 successful responses and zero failures. A separate screenshot attempt timed out waiting for centre elevation even though it received 28 successful tile responses; this remains an unresolved intermittent failure, and no live screenshot is claimed. The initial five-location run also timed out completing a profile and therefore did not pass end-to-end. Live VIC/NSW parcel alignment and runtime source switching remain unverified.
