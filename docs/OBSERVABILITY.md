# Alpha 3 operational diagnostics foundation

Official Planning and parcel/address requests emit `landos_provider_health` structured platform log events containing only a fixed public-source ID/provider, healthy/unavailable/failed status, last-success/last-failure timestamps, response latency and observation time. They never include submitted geometry, address, account/Workspace/Property IDs, share tokens, photo URLs or provider error objects. Request/timeout/query parsing failures preserve saved Workspace data and show a clear unavailable message. A failed Planning source does not discard successful results from other sources; absence is not proof of no restriction.

Instance-local diagnostics hold at most 100 reviewed source keys. Authenticated `/api/providers/health` returns only the current instance's observations, with explicit scope/limitation. Serverless routes/instances may have independent memory or reset; an empty response is **not** proof of health. Durable operational history must be read from the platform's structured logs and its actual plan retention, not inferred from this process map. This is not a distributed uptime monitor or automatic source enablement.

API failure logging now emits fixed event/category fields rather than arbitrary exception messages. Authentication failures are distinguishable without logging email, session or cookies. Ordinary request errors retain their existing UI/API contract. Framework 5xx/runtime events remain available through deployment logs. Workspace child-render failures use the current Next.js `error.tsx`/retry boundary and emit only `frontend_fatal`; photo upload failures persist their failed queue row before emitting `upload_failed`. The best-effort browser reporter deduplicates each category per minute and uses the existing WKWebView-compatible timeout abstraction; a diagnostic failure cannot block the queue. `/api/telemetry` requires current membership and same-origin POST, allows only these two fixed categories, rejects extra fields/over-1KB bodies and has a bounded per-account process budget. No error message, stack, request URL, geometry, ID or photo URL is accepted. Server events include the deployment's public commit SHA for release correlation. Anonymous visitors cannot submit diagnostics.

Share limiter/gateway failures emit fixed `landos_share_budget_exceeded`, `landos_share_abuse` and `landos_share_resolution_failed` events with bounded log frequency and no caller/token/value. The Postgres gateway now supplies distributed caller/token enforcement; logs are the aggregate operational signal rather than the enforcement store. `src/instrumentation.ts` emits `landos_server_error` for captured server failures using only framework route pattern/type, release and time. It deliberately excludes the concrete request path, headers, error message/stack and request body.

Minimal production signals are available from Vercel structured logs:

- API 5xx rate: count/rate of `landos_server_error`, grouped by fixed `route_pattern` and `release`.
- Provider failures and average latency: `landos_provider_health`, grouped by reviewed provider ID/status; average `latency_ms` over healthy and failed calls.
- Upload failures: `landos_client_failure` with category `upload_failed`.
- Auth failures: `landos_api_failure` with category `authentication`.
- Share abuse: `landos_share_abuse` and `landos_share_budget_exceeded`; HTTP 429 remains the client-visible result.

Initial review thresholds: alert on any sustained server-error increase over the preceding release baseline, three consecutive provider failures or a five-minute provider failure majority, repeated upload/auth failure growth, and recurring share-abuse events. Establish numeric production thresholds after real Alpha traffic rather than inventing a normal rate from synthetic tests. Vercel dashboard alert creation and actual log-retention entitlement still require account/dashboard access; the emitted schemas and suggested queries are ready now.

Aggregate operational coverage is provider health, API/auth failures, frontend route-boundary failures, upload failures, share abuse/gateway failures and captured server failures. Root-layout/event-handler failures not captured by Next or disconnected best-effort telemetry can still be absent. This is not an offline diagnostic queue.

Validation: client tests reject photo URL/geometry/arbitrary-event payloads and verify exact request body/deduplication. Browser/API tests verify owner 202/no-store, sensitive-field rejection and anonymous denial; Field retry regression remains required. Provider unit checks verify success/failure timestamps, exact emitted schema, invalid-key rejection and bounded state. Planning unit/API/browser regressions separately verify failure/no-result/unsupported distinctions and independent-source degradation. Physical weak-network/device acceptance remains pending signing.
